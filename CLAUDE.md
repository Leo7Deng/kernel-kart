# Kernel Kart

A one-button kart racer in plain JS on a canvas (ES modules under `js/`, Vite for dev/build). Racers are programming-language mascots (Gopher, Ferris, Pyth, Octo, Tux, Duke, Docky, Swifty, Cpp, Bugdroid), items are dev terms (Turbo, Rubber Duck, Segfault, malloc, sudo, Kernel Panic, Pull Request...). 20 tracks, offline races and cups for 1-4 players, time trial, and LAN online rooms. Live at https://leo7deng.github.io/kernel-kart/.

`README.md` is the player-facing description of every track, item and racer: keep it in sync. Details live in `docs/`:
- `docs/code-map.md`: every file and system in depth (read the part you're touching before changing it).
- `docs/tracks.md`: how to make a track, and every track mechanic (rule, bot logic, key numbers).
- `docs/status.md`: decisions per track/system (why things are the way they are).
- `docs/balance.md`: how balance is judged.

## How we work (the user's standing rules)
- **One commit per change; the subject is one player-facing sentence** (it shows in the game's What's new). End commit messages with the Co-Authored-By line from the session.
- **Keep "In the works" current** (`js/roadmap.js`, the menu's dialog): every job gets an entry when it starts (`'queued'` if waiting) with its start time and an earliest-latest range from similar jobs (small art 10-25 min, a new map or the menu 1.5-2.5 h, more with several helpers); check running helpers about every 20 min and revise; remove the entry once committed. Ideas nobody's on go in `ideas`. Roadmap-only commits are hidden from What's new.
- **Helpers:** the main session fans work out to helper agents in git worktrees (one task each, own files where possible), then merges and reports. At most ~3 running when the machine is busy; pause/queue long ones (TaskStop, resume with SendMessage).
- **Test lightly, always** (the user: "its unacceptable to do this much testing everytime, its way too wide and long"): after a change or a merge run only the one quick check that covers it (`npm run typecheck`, plus the single test for what changed, e.g. `node test/fight.test.mjs` for a kit, `node test/sim.test.mjs` only when race code changed); drawing/UI/docs changes need just typecheck + build. No full test sweeps on every merge; the heavy suites (net, timetrial, mega, balance runs) only when their area changed. Run anything heavy with `nice -n 19`.
- **Never kill servers or browsers you didn't start.** Use your own ports for dev servers (`npx vite --port 52xx --strictPort`) and headless Chrome debug ports (`.claude/kk-tools/cdp-online.mjs` has a CDP driver).
- **Keep workflows fast**: **one measuring job at a time** on the 4-core VM (it gets every core; others do art/UI/code meanwhile; several at once slow everyone). **Measure in two passes**: explore with small runs (`node test/fight-vs-field.mjs <id> <lv> <lv> 16`, `node test/fight-dig.mjs <a> <b> <lv>`, `npm run balance -- 160`, `node test/solo-pace.mjs 2`), then ONE big confirming run (fight-odds 40 a pair, balance 640) on the final change. fight-odds is incremental (re-measures only the matchups of changed kits, `test/fight-odds-cache.json`; `--full` for all); fight-odds, fight-vs-field and balance take `--until=<±>` to stop once precise enough. **Screenshots: 2-3 sizes** (1280x720, 1024x768 iPad, 390x844 iPhone), with `.claude/kk-tools/shoot.mjs` (one Chrome, `&shot` URLs that skip the 3D warm-up). A useful one-off measuring script goes in `test/` (repo-relative imports, a usage header), never `/tmp`. Helper briefs stay short and point at `/home/super/Projects/kernel-kart-vm/helper-rules.md`'s cheat sheets.
- **Write concisely, keep the detail** ("the long texts are adding up just everywhere", then "dont lose the detail, i just wanted you to debloat"): say each fact once in fewer words (no padding, repetition or restating the code); never drop facts players or future sessions use (numbers, rules, per-track/item/racer/move details, the user's decisions and reasons). New comments: a line or two, no dated history or old values (git has them). New docs/status.md entries: short (decision, reason, key numbers). Balance notes: the reason and current numbers.
- The user plays via `npm run play` (a `.play` worktree kept at HEAD; F9 reloads to the newest commit) and online with friends over LAN, often on iPads and iPhones.
- `npm run publish:web` updates the web version: one no-history snapshot on `main` and `gh-pages`, by an address no GitHub account has, every file linguist-vendored. Never push the local history (a private email; the user wants neither the commits on their profile nor the code in their language stats).

## The user's taste (decisions that keep coming up)
- Cute, simple, cartoony but believable art; not realistic or metallic. Effects sparing and meaningful, no words in effects (events go in the icon feed).
- Catch-up is items only (no speed help for cars behind). Some maps may favour front-running (e.g. Moonshot's rocket rows).
- Online: every screen frames every player (yours first). No split screen, ever.
- Drift is on by default (a third key); bots drift too. Burnout at the start is harsh and obvious.
- Looks: Settings → Style. **Only Classic Flat is worked on**: new art and UI must look right there; Classic (the default) shouldn't break; Racing and Premium are archived (no extra time on them). Flat-look code lives in `bold()` branches with the `BK` palette (`js/look.js`). 3D models (experimental) behind a Settings toggle (`js/art/model3d.js`).

## Rules that keep things working
- **Determinism:** gameplay code never calls `Math.random` (it only seeds `race.rng` / `car.rng`); cosmetics use `frnd`/`fchance`. Gameplay files import `Math` from `js/detmath.js` (`import { Math } from './detmath.js'`: the same bits on every computer, which the engine's own don't promise) and never use `**` (write `Math.pow`). Nothing a race changes may outlive it (module caches, the shared track). `test/determinism.test.mjs` checks all of this. Replays, measurements and the golden depend on it.
- **The golden:** `test/golden.json` records every test race. A refactor or drawing change must keep it byte-identical; an intended gameplay change regenerates it (`node test/sim.test.mjs --update`, `git add test/golden.json` after) and says why in the commit. If others have uncommitted edits, regenerate in a clean worktree of HEAD.
- `race.js` and everything it imports must load in Node without a DOM (the tests import it). DOM code stays in `render.js`, `ui.js`, `input.js`, `main.js` and the `*-ui.js` files.
- Track mechanics only some tracks have go through `race-mechanics.js` (`T.mech` null otherwise, so other tracks replay identically); per-race state lives on the race (plain data, so online snapshots carry it), never on the shared track.
- **Type checks** (`npm run typecheck`, part of `npm test`; must stay at 0 errors): TypeScript checks plain JS with JSDoc types (`jsconfig.json`, no build step). A file is checked when its first line is `// @ts-check`: the fight core and every kit, the race core (race.js, geometry.js, race-mechanics.js, detmath.js) and the online session (net.js, net-sync.js, net-room.js, fight-net.js). Shared shapes are `@typedef`s next to their owner: the kit API in `js/kits/index.js` (Plugin, FighterData, Move, Kit, BotHooks, BotCtx, Seen), the fight's in `js/fight.js` (Fight state, Fighter, WorldObj, FightEvent, FightConfig), Track/TrackDef in `geometry.js`, Car/Racer/RaceConfig in `race.js`, Snap in `net-sync.js`, Session/RoomPlayer in `net.js`, RoomCfg in `net-room.js`; `js/types.d.ts` (checker only) holds what JSDoc can't say (Race's mixed-in methods, Fight's non-enumerable `A`/`rngs`). A new core module starts with `// @ts-check` and types its exports; a kit annotates its `fighter`, `kits`, `objs` and `ai` as `_template.js` does. Details: docs/code-map.md "Type checks".
- A new map/mechanic: bots must handle it (a mechanic the AI ignores makes balance meaningless); a layout change bumps the track's `rev` (time-trial ghosts set aside).

## Run and test
- `npm run play` (what the user plays), `npm run dev` (the working tree), `#demo=N` auto-starts an all-bot race on track N, `npm run build` → `dist/`, `npm run server` (dist + the online relay).
- `node test/sim.test.mjs` (every track × level × seed against the golden, the same on every computer), `node test/determinism.test.mjs` (races don't depend on what ran before them; gameplay maths is portable), `node test/net.test.mjs` (relay + online sync on every track), `node test/timetrial.test.mjs`, `node test/mega.test.mjs`, `node test/drift.mjs`. `npm run typecheck` (the type checks, above). `npm test` runs them all.
- Measurement tools: `npm run items` (item value by position), `npm run balance -- 640 [--drift]`, `npm run boxes` (single boxes), `npm run odds` (README's odds table), `node test/drift-bots.mjs`, `npm run frontrun` (each track's Front-runner score for the menu, `js/frontrun-data.js`: re-run a reworked track with `npm run frontrun -- 96 <index>`; see docs/balance.md). Fight: `npm run matchups` (`test/fight-odds.mjs`, the select screen's odds), `node test/fight-roundrobin.mjs`, `node test/fight-levels.mjs`. All of them spread their races or fights over every core (`test/pool.mjs`, results in job order, so they print exactly what one core would); `--jobs=N` sets how many workers.

- `js/race-mechanics.js` + one `js/race-<name>.js` per mechanic; drawing in `js/draw-mechanics.js` and `js/art/*.js` (one file per theme/set piece); `js/tracks.js` definitions; `js/geometry.js` track building.
- Online: `server/relay.mjs` (WebSocket relay), `js/net.js` session, `js/net-sync.js` snapshots/prediction, `js/net-room.js` room rules, `js/net-ui.js` room screen, `js/net-chat.js` + `js/chat-ui.js` chat.
- Time trial: `js/timetrial.js`, `timetrial-ui.js`, `draw-timetrial.js`. Clips: `js/clip.js`, `clip-ui.js`. Audio: `js/audio.js` (all synthesised).
